# ADR-0004: Super-Repo Structure

**Status:** Accepted  
**Date:** 2026-03-03  
**Authors:** Jun (Principal DevEx)

---

## Context

The 9TEVE-OS stack is assembled from multiple upstream projects (SWE-AF, OpenHands, n8n, Prefect, Mem0, Vault, LobeHub). Without a cohesive repo structure, shared standards, and integration glue, the system degrades into "a pile of repos" that is hard to reason about, test, or release.

## Decision

We maintain **one umbrella repository** (`9teve-os` / `9TEVE-O`) as the canonical product surface. Upstream forks are kept as thin adapters rebased against upstream, never fork-modified for integration.

### Repository Layout

```
9teve-os/
├── README.md
├── ADR/                         # Architecture Decision Records
├── docs/
│   ├── architecture/            # System design docs
│   ├── runbooks/                # Operational runbooks
│   └── threat-model/            # STRIDE + mitigations
├── specs/
│   ├── control-plane.openapi.yaml
│   ├── policy-schema.json
│   ├── action-envelope.json
│   └── telemetry-contract.md
├── src/
│   └── able_to_answer/
│       ├── api/                 # FastAPI app + route handlers
│       ├── audit/               # Audit-pack builder
│       ├── control_plane/       # Run/task lifecycle + policy enforcement
│       ├── core/                # Config, storage, logging
│       ├── ingestion/           # Text chunking + document upsert
│       └── retrieval/           # Lexical scoring + top-k chunk retrieval
├── tests/
│   ├── test_api.py
│   ├── test_units.py
│   └── test_control_plane.py
├── integrations/
│   ├── github/                  # GitHub Actions + PR automation
│   └── gemini-cli/              # Gemini CLI adapter stub
├── templates/
│   ├── repo-template/           # New service scaffold
│   ├── service-template/        # Microservice scaffold
│   └── function-pack-template/  # Function pack scaffold
└── scripts/
    ├── dev/                     # Local dev helpers
    └── ci/                      # CI helper scripts
```

### Adapter Pattern

Do **not** fork-modify upstream projects. Instead, write thin adapters in `src/able_to_answer/` that talk to upstream public interfaces. This keeps upstream forks minimal and rebased.

### Canonical Single Sources of Truth

| Artefact | Location |
|----------|----------|
| Policy schema | `specs/policy-schema.json` |
| Action envelope | `specs/action-envelope.json` |
| Telemetry contract | `specs/telemetry-contract.md` |
| OpenAPI spec | `specs/control-plane.openapi.yaml` |

### CI Enforcements

Every PR must pass:
- Linting (Python: `ruff`; YAML: `yamllint`)
- All tests (`pytest tests/ -v`)
- Policy evaluation dry-run on changed policy profiles
- Artefact pack generation for releases

## Consequences

- **Positive**: Single source of truth; uniform CI; discoverability.
- **Negative**: Monorepo can become large; requires disciplined module boundaries.
- **Mitigation**: Keep `src/able_to_answer/` modules decoupled; use adapters for external services.
