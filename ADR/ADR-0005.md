# ADR-0005: Minimal Viable 9TEVE-OS Plan

**Status:** Accepted  
**Date:** 2026-03-03  
**Authors:** Elena (Product Engineer)

---

## Context

The goal is to demonstrate 9TEVE-OS as a working, defensible operating system for AI-assisted software engineering. "Done" means: a user submits a natural-language goal and the system creates a run, plans tasks, executes with an agent, enforces policy gates, and outputs artefacts + docs.

## Decision

### MVP Scope (90-day)

#### Must Have ✅ (implemented)
- **Control Plane** — basic run/task state machine (`/v1/runs`, `/v1/tasks/*`)
- **Policy gate** — allow/deny + pending_approval for side-effect actions (three built-in profiles: `default`, `strict`, `permissive`)
- **Artefact store** — content-addressed, immutable; linked to runs
- **Policy evaluation** — dry-run endpoint (`/v1/policies/evaluate`) for testing policy before execution
- **Document intelligence** — ingest → retrieve → answer → audit (the `able-to-answer` core)

#### Should Have (next sprint)
- **Agent runner adapter** — start with SWE-AF (thin adapter in `integrations/`)
- **Vault broker stub** — `CredentialRef` interface backed by `ATA_*` env vars; swap for real Vault without API change
- **Structured telemetry** — W3C trace propagation; structured JSON logs (see `specs/telemetry-contract.md`)
- **Memory integration** — Mem0 adapter for storing run summaries + decisions

#### Could Have (90-day horizon)
- Compliance evidence pack (Comp integration)
- Formal model checks in CI (TLA+ invariants for state machine)
- Workflow adapter (Prefect or n8n)

### MVP Happy Path

```
1. POST /v1/runs          { tenant_id, goal, policy_profile_id }   → { run_id }
2. POST /v1/runs/{id}/tasks { type: "code", agent_role: "coder" }  → { task_id }
3. POST /v1/tasks/{id}/dispatch { action_type: "GIT_COMMIT" }      → { status: "dispatched" }
   (or "awaiting_approval" for GIT_PUSH with default profile)
4. POST /v1/runs/{id}/approve   { approved_by: "alice" }           → { approved_tasks: 1 }
5. POST /v1/tasks/{id}/complete { outputs: { pr_url: "..." } }     → { status: "completed" }
6. GET  /v1/runs/{id}/artifacts                                    → [ audit_pack, ... ]
```

### First Three Function Packs

A **function pack** is a versioned bundle: spec (OpenAPI/JSON schema) + implementation stub + tests + docs page + policy tags.

1. **Repo Reverse Engineer Pack** — analyse a repository and produce a structured architecture summary
2. **Policy Doc Condenser Pack** — ingest policy documents and extract allow/deny rules into `policy-schema.json` format
3. **Audit Pack Builder** (already implemented) — standardise artefacts from a run into the canonical audit pack format

### Definition of Done

A single integration test that exercises the full happy path above, produces a non-empty artefact list, and asserts that a `GIT_PUSH` action with the `default` policy profile reaches `awaiting_approval` before `approve` is called.

## Consequences

- **Positive**: Delivers a working demo of the full governance loop in < 90 days.
- **Negative**: The MVP stub for Vault and agent runners means real agent execution is simulated.
- **Risk**: If policy evaluation performance degrades, all runs are blocked. Mitigation: PDP caching (profile_id + action_type key).
